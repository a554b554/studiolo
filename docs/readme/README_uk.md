# Studiolo

### Один робочий простір для всіх CLI агентів кодування, за які ви платите, на кожній вашій машині.

## Встановлення за допомогою агента кодування

Вставте це в Claude Code, Codex або будь-який агент кодування, що може виконувати команди на машині, яку ви хочете використовувати:

```text
Встанови Studiolo з https://github.com/a554b554/studiolo: клонуй репозиторій, переконайся, що доступний Node.js 22.14+ і що встановлено CLI `claude` та/або `codex`, запусти `node src/server.mjs` з кореня репозиторію, перевір, що http://127.0.0.1:4310 відповідає, а потім скажи мені відкрити Settings → Hosts & accounts, щоб увійти в мої облікові записи. Сам ні в що не входь.
```

Або вручну:

```sh
git clone https://github.com/a554b554/studiolo studiolo && cd studiolo
node src/server.mjs        # http://127.0.0.1:4310
```

Studiolo не має залежностей npm; `npm install` не потрібен. Тести: `node --test test/*.test.mjs`.

## Що це таке

Studiolo — це самостійно розгорнутий вебробочий простір, що керує CLI **Claude Code** і **Codex**, уже встановленими на ваших комп'ютерах. Це не черговий чат-інтерфейс поверх ключа API:

- **Ваші підписки, ваші CLI.** Кожен запит проходить через справжній процес `claude` або `codex` — ті самі інструменти, skills, сервери MCP, режими дозволів і поведінка агента, що й у терміналі. Вхід за підпискою або ключ API — на ваш вибір для кожного облікового запису.
- **Облікові записи для кожної машини під керуванням Studiolo.** Входьте в кілька облікових записів Claude і Codex на кожному комп'ютері з браузера. Кожен обліковий запис отримує власний ізольований каталог конфігурації CLI; ваші особисті `~/.claude` чи `~/.codex` не зачіпаються. Квота кожного облікового запису показується в реальному часі.
- **Одна історія проєктів на всіх машинах.** Проєкти зберігаються в теці, яку ви синхронізуєте як завгодно (наприклад, Syncthing). Історія розмов — це журнал лише для дописування, що зливається детерміновано; кожна машина запускає той самий сервер і віддає ту саму історію. Розмова виконується на машині, яку ви для неї обрали; читати й продовжувати її можна з будь-якої.
- **Досвід термінала — у браузері.** Зупиняйте хід клавішею Esc, скеровуйте агента під час роботи додатковим повідомленням, вводьте `/` для власних slash-команд CLI — усе це відображено на нативні протоколи, а не реалізовано заново.
- **Artifacts і коментарі на сторінці.** Вебзастосунки, які створюють агенти, працюють як Artifacts зі сталими бекендами та синхронізованим сховищем; виділіть щось у попередньому перегляді й надішліть агентові як завдання.

## Швидкий старт

1. **Передумови** — Node.js 22.14+ і встановлений на машині CLI `claude` та/або `codex` (`claude --version`, `codex --version`).
2. **Запустіть** `node src/server.mjs` і відкрийте <http://127.0.0.1:4310>.
3. **Додайте облікові записи** — Settings → *Hosts & accounts* → *Add account*. Оберіть машину, тип (Claude Code / Codex) і спосіб входу, а потім виконайте показані кроки (див. нижче).
4. **Створіть проєкт, почніть розмову** — у полі введення обираються **машина → обліковий запис → модель → зусилля → режим дозволів**. Перше повідомлення фіксує машину й обліковий запис для цієї розмови; модель, зусилля та дозволи можна змінювати для кожного повідомлення. Інша модель продовжує ту саму нативну сесію, а її перший хід заново читає контекст без кешу промпту.

Змінні середовища: `STUDIO_STATE_DIR` (приватний стан машини, за замовчуванням `~/.studio-local`), `STUDIO_BIND`, `STUDIO_PORT` (4310), `STUDIO_PREVIEW_PORT` (4311), `STUDIO_TOKEN`, `STUDIO_UPLOAD_LIMIT` (байти, за замовчуванням 100 МБ). Один сервер на каталог стану.

## Облікові записи та вхід

Облікові записи належать машині й створюються з браузера. Кожен обліковий запис — це каталог у `~/.studio-local/accounts/<id>/`, що використовується як `CLAUDE_CONFIG_DIR` або `CODEX_HOME`, тож кілька облікових записів одного CLI співіснують, а власний вхід вашого термінала ніколи не зачіпається. Під час створення облікового запису Studiolo наповнює цей каталог із вашого стандартного каталогу CLI — копіює `settings.json` / `CLAUDE.md` (Codex: `config.toml` / `AGENTS.md`) і створює посилання на `skills`, `plugins` тощо — щоб агенти зберегли skills і сервери MCP, якими ви вже користуєтеся. Облікові дані ніколи не копіюються.

| Тип | Спосіб | Що відбувається |
| --- | --- | --- |
| Claude Code | **Підписка** | Studiolo запускає `claude auth login`; ви відкриваєте посилання, входите й вставляєте код авторизації назад на сторінку. |
| Claude Code | **Ключ API Anthropic** | Ключ зберігається в каталозі облікового запису (режим 0600) і передається як `ANTHROPIC_API_KEY`; перевіряється через handshake CLI, відкидається, якщо його відхилено. Оплата за використання, без вікон квоти. |
| Codex | **ChatGPT** | Код пристрою через app-server Codex: сторінка показує посилання та одноразовий код; увійдіть із будь-якого браузера, сторінка оновиться після завершення. |
| Codex | **Ключ API OpenAI** | Зберігається самим Codex у `CODEX_HOME` облікового запису. |

Після входу Studiolo зчитує ідентичність облікового запису (e-mail, тариф) і список моделей безпосередньо з CLI — без витрачання жодного запиту до моделі — а для Claude ще й slash-команди CLI для автодоповнення в полі введення. Обліковий запис без власної назви перейменовується на свій e-mail, тож поле введення, заголовок розмови, кожна відповідь і панель використання показують, хто говорить. Облікові записи можна перейменовувати, оновлювати, виходити з них (`claude auth logout` / `codex logout`) або видаляти; розмова, чий обліковий запис видалено, може продовжитися з іншим обліковим записом на тій самій машині.

Панель використання (внизу ліворуч) відповідає машині, обраній у полі введення: підписки Claude показують 5-годинне вікно, Codex — тижневе, облікові записи з ключем API тарифікуються за використанням. Вона зчитує власні endpoints використання CLI (`get_usage`, `account/rateLimits/read`), кешує на 60 с, ніколи не опитує періодично й ніколи не запускає CLI для облікового запису, з якого вийшли.

Усе це працює і для віддалених машин: оберіть інший хост онлайн у *Hosts & accounts*, і запити буде передано йому.

## Чат як у CLI

Кожна розмова має власний резидентний нативний процес — Claude Code через двонаправлений `stream-json`, Codex через `app-server` — тож агент поводиться точно як у терміналі. Веб-елементи керування відображаються на нативні протоколи:

| У терміналі | У Studiolo | Як |
| --- | --- | --- |
| Esc, щоб зупинити | **■ Stop** або Esc у полі введення | Керівний запит `interrupt` у Claude / `turn/interrupt` у Codex. Процес і нативна сесія зберігаються; часткова відповідь лишається; наступні повідомлення продовжують ту саму сесію. |
| Вводити, поки агент працює | Надіслати під час ходу = **Steer** | Claude зчитує це на наступній межі інструмента; Codex — `turn/steer`. Показується як *You · steer*; відповідь продовжується в новому сегменті. **Queue** натомість надсилає після ходу. |
| `/compact`, `/context`, власні команди, skills | Введіть `/` для списку команд | Команди Claude передаються дослівно (список надходить від самого CLI). У Codex немає текстових команд; `/compact`, `/review`, `/skills`, `/mcp` відображаються на запити app-server. |
| — | `/model`, `/effort`, `/mode`, `/rename`, `/new`, `/status`, `/clear`, `/stop`, `/help` | Команди платформи, що обробляються в браузері або чергою. |

Запити дозволів, які CLI поставив би в терміналі, з'являються на сторінці: схваліть один раз або відхиліть, і те саме виконання продовжиться. Автоматичний режим — власний режим CLI (Claude `auto`, Codex `auto_review`); Studiolo ніколи не додає прапорців обходу чи постійних правил дозволу. Зусилля міркування та модель можна змінювати для кожного повідомлення в межах розмови (Claude `set_model` / `apply_flag_settings`, параметри `turn/start` у Codex).

Поки виконується хід, розмова показує роботу так само, як CLI: те, що агент каже між кроками, лишається повністю, послідовні виклики інструментів згортаються в один рядок, який можна розгорнути, а поточний крок і витрачений час завжди видно; коли надходить відповідь, увесь хід згортається у свій raw log. Надіслане повідомлення з'являється одразу й доставляється у фоні (у разі помилки можна повторити). На бічній панелі обертовий індикатор позначає розмови та проєкти, які зараз працюють, а крапка — результати, яких ви ще не бачили.

## Кілька машин

Запустіть той самий сервер на кожному комп'ютері; помістіть `projects/` у теку, яку ви синхронізуєте (Syncthing або будь-яка синхронізація файлів). `.studio/events/` кожного проєкту — це незмінний журнал із причинним упорядкуванням; машини онлайн також обмінюються журналами напряму, тож зміни з'являються за лічені секунди. Будь-яка машина може показати всі розмови; виконання завжди відбувається на машині, до якої прив'язано розмову, а нативні сесії CLI ніколи не мігрують.

**Доступ до інших машин.** Найпростіше безпечне налаштування — [Tailscale](https://tailscale.com): покладіть `tailnet.json` (`{"enabled":true,"command":"tailscale"}`) і випадковий `access-token.txt` (≥ 32 символів) у каталог стану, запустіть як зазвичай, і Studiolo опублікує свій порт за допомогою `tailscale serve`; відкрийте `http://<machine>:4310` і введіть токен один раз. З `"trustTailnet":true` токен для трафіку tailnet не потрібен. Без Tailscale прив'яжіть сервер до приватної адреси через `STUDIO_BIND` і задайте `STUDIO_TOKEN`. Сервери знаходять один одного через `projects/.servers/` або через ручне спарювання в Settings.

**Автозапуск.** macOS: `node scripts/install-studio-macos.mjs` встановлює LaunchAgent (`net.studio-local.server`). Windows: зареєструйте `scripts/start-studio-windows.ps1` як завдання Планувальника завдань (дія `conhost.exe --headless powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -File <path>`, запуск під час входу в систему, без дублікатів екземплярів, повтор щохвилини); `scripts/restart-studio-windows.ps1` перезапускає його після оновлення, щойно не лишиться активних запусків.

**Оновлення.** Файли фронтенду в `public/` зчитуються під час кожного запиту й набувають чинності, щойно синхронізуються; зміни в `src/` потребують перезапуску на кожній машині.

## Artifacts і коментарі на сторінці

Попросіть агента зробити вебсторінку чи застосунок, і він підтримуватиме `studio.artifacts.json` у корені проєкту:

```json
{
  "artifacts": [
    { "key": "game", "name": "Click the target", "root": "game", "entry": "index.html",
      "command": ["node", "server.mjs"], "port": 4320, "dataPaths": ["game/data"] }
  ]
}
```

Статичні сторінки не містять `command`, `port` і `dataPaths`. Кожен Artifact отримує власний сталий порт попереднього перегляду й origin; `localStorage` попереднього перегляду зберігається в проєкті та синхронізується, тож гра, збережена на одній машині, продовжується на іншій. Бекенди працюють як звичайні локальні процеси (не пісочниця) з `PORT` і `HOST`; **Snapshot** зупиняє бекенд і копіює оголошені шляхи даних, **Restore** повертає їх на місце.

У попередньому перегляді *виділіть елемент, текст або область canvas* і напишіть коментар: він стає завданням для обраного вами агента, а виділення — доказом (шлях DOM, цитований текст або PNG із canvas). Коментарі до одного Artifact виконуються по черзі; різні Artifacts і розмови виконуються паралельно. Див. `examples/persistent-game/` (бекенд Node + SQLite + Canvas) і `examples/artifact-compatibility/`.

## Файли та конфігурація

| Розташування | Вміст |
| --- | --- |
| `projects/<id>/` | Робочий каталог проєкту: код, Artifacts, дані (синхронізується) |
| `projects/<id>/.studio/events/` | Авторитетний незмінний журнал розмов |
| `projects/<id>/.studio/state.json`, `history-index.md`, `sessions/`, `artifacts/` | Стан, який можна відтворити, і читабельна історія для агентів |
| `projects/<id>/.studio/artifact-storage/`, `snapshots/`, `attachments/` | Синхронізоване сховище попереднього перегляду, знімки даних, докази коментарів |
| `projects/<id>/uploads/` | Файли, перетягнуті в чат або панель ресурсів |
| `projects/.servers/` | Публічні адреси серверів для виявлення (без секретів) |
| `projects/.deleted/<id>.json` | Надгробки видалених проєктів (синхронізуються); теку, відтворену запізнілою синхронізацією, буде видалено знову |
| `~/.studio-local/` | Приватне для машини: ідентичність, `accounts.json`, `accounts/<id>/`, спарювання, налаштування Tailscale — ніколи не синхронізуйте |
| `~/.studio-local/agent-profiles.json` | Необов'язково: шлях до виконуваного файлу / env для кожної родини CLI (`claude`, `codex`) або для id облікового запису |

Видалення проєкту остаточне (архівування лишається оборотним) і відхиляється, поки робота стоїть у черзі, виконується або очікує. Сервер, що видаляє, записує надгробок, а потім видаляє всю теку `projects/<id>/`; ваш інструмент синхронізації переносить обидва на інші машини. Кожен сервер, побачивши новий надгробок, видаляє свою залишкову копію, резидентні процеси агентів проєкту та порти попереднього перегляду Artifacts, а також транскрипти Claude (`projects/<encoded path>*` у кожному каталозі конфігурації) і rollouts Codex (зіставлені за `cwd` у першому рядку), чий робочий каталог був усередині проєкту. Оброблені ID записуються в `~/.studio-local/purged-projects.json`. Проєкти, м'яко видалені старішими версіями (`deletedAt`), видаляються один раз під час запуску.

## Часті запитання

**Чи використовує він мій ключ API?** Лише якщо ви додасте обліковий запис із ключем API. Облікові записи за підпискою працюють через власний вхід CLI; Studiolo не зберігає жодних власних облікових даних.

**Чи вплине це на мої `claude` / `codex` у терміналі?** Ні. Облікові записи Studiolo зберігаються у власних каталогах; `~/.claude` і `~/.codex` зчитуються лише один раз, щоб скопіювати налаштування та створити посилання на skills.

**Це пісочниця?** Ні. Агенти й бекенди Artifacts — це ваші власні локальні процеси з вашими дозволами, точно як CLI у терміналі.

**Чи можна користуватися ним із телефона?** Так, як браузерним клієнтом через Tailscale; CLI працюють на ваших комп'ютерах.

**Чому нуль залежностей?** Сервер написано на чистому Node.js (ESM, лише модулі `node:`), тож він працює всюди, де працює Node 22, і ніщо в ланцюжку постачання не стоїть між вами та вашими CLI.
